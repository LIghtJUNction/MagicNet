# 内核同步与连接资源归属

连接结束后，连接对象、流记录和关闭回调必须一起完成交接或清理；同步上游时保留这一规则和现有协议能力。

## CORE-001：固定同步对象

本轮起点为 `LIghtJUNction/sing-box@871b7a3440cd9c850f1b09ef3b4ada9babb4384b`，同步目标为 `SagerNet/sing-box` 的 testing 提交 `e5d91fa79f6319d5de940d6c81d81f0fe53b9476`。继续使用 1.15 预发布轨道；提交身份、上游标签和产品显示版本分别记录。该目标位于 1.15.0-alpha.13 之后，产品构建须附实际 fork revision。

同步范围包括上游 `sing-tun` 的连接生命周期改动、路由握手失败的退出路径及 WireGuard 复制源码的完整上游差异。逐项处理本 fork 的差异，保留 AWG、eBPF、VLESS Encryption 和全部现有 release build tags。依赖的版本、替换项与 go.sum 一起固定；构建使用只读模块解析。最终采用的 fork 和 Android 实现完整 SHA 写入 PROVENANCE、VERIFICATION 与 gitlink。

## CORE-002：握手失败完成清理

TCP/UDP 路由在握手阶段失败时，关闭本次建立且仍归当前处理方所有的连接；如提供 `onClose`，向它传递对应失败。连接关闭和回调都在该路径完成，不能只退出函数而将流记录留到超时回收。

成功路径将连接及关闭责任交给现有转发链；错误路径只清理一次。保留错误上下文、取消和超时语义，复用现有关闭辅助函数，避免为单个协议复制第二套资源管理机制。

## CORE-003：绑定与关闭可以并发

`AttachFlow` 与 `CloseFlow` 共享一个受同步保护的生命周期状态。关闭发生在绑定前时，后到的连接立即关闭；绑定先完成时，由关闭路径取走并关闭已绑定连接；同时发生时最终结果与这两种顺序之一一致。

关闭后清除记录持有的连接引用。外部 `Close` 调用和关闭回调在内部锁外执行，以支持阻塞关闭和重入而不死锁；重复关闭保持幂等。测试用明确的同步点安排先后顺序，并配合竞态检测。

## CORE-004：内存证据来自实际对象

首先检查失败连接、流表条目、缓冲区、计时器与 goroutine 的归属和释放条件。重复创建并结束同一类流后，活动对象应回到该夹具的基线；保留超时资源时，明确其有界大小和回收条件。

测量使用相同工具链、build tags、配置、输入规模和 Go 运行时参数，分别报告累计分配、存活堆、峰值或采样 RSS，以及 CPU/延迟开销。每项记录源码 SHA、运行次数与统计口径。无测量时记录修复的资源路径及剩余未知；宿主局部结果仅适用于对应路径。现有 `GOMEMLIMIT` 分档、用户覆盖、TUN 默认 stack 和协议能力保持原合同，不能用降低预算或删除功能替代代码修复。

## CORE-005：集成与兼容

先提交本合同，再实施内核同步与修复。候选内核形成可追溯提交后，分别完成宿主测试、生产 tags 构建、Android arm64 交叉构建和真实核心配置检查；按实际环境单列结果。随后在保留最新 UI 与生命周期修复的 Android main 上更新内核 gitlink，最后更新 MagicNet 的实现 gitlink。

沿用 `run`、`check`、`version` 和现有本地 Clash API。二进制元数据包含实际 fork revision 与 build tags，配置仓库 `MagicSingBox` 与规则数据按各自原固定点使用。Android 安装、实际 TUN/eBPF 挂载、AWG/WireGuard 对端、热点流量和长期内存测试单独记录，构建成功不替代这些运行证据。
