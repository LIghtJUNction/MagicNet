# 软件质量合同的验收条件

这些条件用于检查质量要求是否转化为具体设计和实现证据。不得只因代码能编译、测试通过或页面有装饰效果就宣布全部满足。

## 设计与呈现

1. 若项目有 UI，交付说明能指出目标用户、主要任务、视觉层级和设计决定，并能从实际界面中观察到它们。
2. 页面布局符合真实内容；每种主要屏幕状态（正常、空、加载、错误、成功、禁用）都有适当呈现，移动/窄窗口与键盘操作得到检查。
3. 配色、文字、间距、图标和动效有一致规则；若无障碍或 reduced-motion 适用，完成相应检查。
4. 不使用无意义的占位文字、虚构数据、未授权资产或无产品理由的通用 AI 视觉套路。没有实际打开 UI 时，视觉验收标记为未验证。
5. 非视觉项目的 CLI、API、错误和文档有清楚层级、稳定命名和可理解的反馈。

## 代码品味

1. 变更沿用仓库约定，模块责任清楚，依赖方向能解释；共享业务规则或设计 token 没有多份手工真相源。
2. 新增抽象对应真实重复或稳定领域概念；无死代码、无用依赖、吞异常、占位实现或无理由的复制粘贴。
3. 错误输入、超时、取消、部分失败及资源释放按产品语义处理；公共接口和持久数据变化有兼容性说明。

## 性能

1. 指明被测关键工作流、目标设备/runtime、数据或并发规模和指标；没有预算依据时明确标记待确认，而非编造阈值。
2. 性能结论带有实际命令、环境、测量方法和可复现数据；未运行的基准不标为通过。
3. 关键热点有基线；改动后用同样负载和环境复测，并报告正确性、安全性及维护成本是否保持。
4. 对明显的高复杂度、无界资源增长、重复请求、无界并行或过大客户端/发布工件给出分析与处理结果。

## 交付记录

说明检查了什么、证据在哪里、执行了什么、结果如何、哪些目标尚待确认或未验证。未满足的条目要保留为缺口，不能通过降低目标或省略失败结果伪造通过。
