# 豫见郑大 App 页面加载失败：ADB 实机诊断

- 日期：2026-11-20（UTC+8）
- 项目：MagicNet
- 检查对象：豫见郑大 `com.supwisdom.zzu`，版本 1.1.7；Android 16
- 当前状态：已定位到校园访问认证响应异常；页面恢复尚未验收
- 本记录不包含账号、设备序列号、Cookie、认证票据、订阅信息或个人页面截图。

## 结论

校园 App 能够与校园服务器建立 HTTPS 连接，但部分业务接口返回到学校认证门户的 HTTP 302 跳转，随后出现认证页面的 HTML 响应。关闭 MagicNet 并确认核心进程、透明代理数据面均停止后，同类跳转仍然出现。因此，“只要停用 MagicNet 就能恢复”已被本次实测否定。

现有证据支持把恢复重点放在 App 与学校访问网关之间的认证会话。它不支持直接认定账号密码错误，也不足以把“登录密钥过期”确定为唯一原因。重新认证后的页面和接口结果，才是修复是否成立的验收依据。

## 1. 用户可见现象

实机观察到日程页提示“网络错误”；冷启动后的首页显示“页面正在建设中”。这些文字是失败现象，不能单独证明校园服务器正在维护。

调试期间手机也被正常用于其他应用，因此部分截图对照不满足校园 App 持续处于前台的条件。未把这些截图当作有效的修复验证。

## 2. 网络基础检查

MagicNet 处于 TUN 模式，`magicnet0` 正常，校园域名连接命中教育域名直连规则，最终走 direct。没有观察到这些业务连接被广告规则直接拦截。

| 检查 | 观察 | 证明范围 |
| --- | --- | --- |
| root HTTPS 直连与本机混合代理 | 校园入口返回 200/302；未出现 TLS 证书校验错误 | 基础连接和 TLS 可用 |
| 普通 Android UID 经真实 TUN 访问 nox | HTTP 200，响应完整 | 普通应用能够经 TUN 联网 |
| 普通 UID 访问 info | 跟随 3 次跳转后 HTTP 200，响应完整 | 只能证明最终网页可达，不能证明业务接口或登录成功 |
| 普通 UID 访问 generate_204 | HTTP 204 | 对照网络请求成功 |
| 校园 App 自身 TLS 明文事件 | 出现校园业务请求和实际 HTTP 200/302 响应 | 校园 App 并非完全无法联网 |

“200”只表示该次 HTTP 请求拿到了一个成功响应；如果最终拿到的是登录网页，校园业务数据仍然不可用。

## 3. 实际认证跳转证据

使用设备现有 eCapture，限定校园 App UID、Conscrypt TLS 库和短时间窗口。原始明文仅在内存处理，持久化结果只保留脱敏元信息。

关键证据来自响应的 `Location`：网关在 `redirect_url` 中声明原始业务目标。报告只保存该目标的主机名和路径，删除所有查询值。

| 原始业务目标 | 实际响应 | 跳转目标 |
| --- | --- | --- |
| `info.s.zzu.edu.cn/portal-api/appVersionInfo` | 302，text/html | `nox.zzu.edu.cn/portal.php` |
| `info.s.zzu.edu.cn/portal-api/portalApi/api/open/app/menu` | 302，text/html | `nox.zzu.edu.cn/portal.php` |

同一校园 App 捕获窗口还观察到 `/api/v1/sso/tac`、`/authn/base/` 的请求、相应认证跳转，以及 `200 text/html; charset=utf-8`。同时存在 `code: 0`、消息为“已登录”的 JSON 响应，说明不能把本次问题简单描述为“App 根本没有登录”。

### 配对限制

该设备的 hook 事件没有有效的 FD/Tuple，不能把不同线程、连接的相邻请求与响应强行配成一对。初步按 FD 排队的结果存在错配风险，未用于本记录的逐接口结论。上表使用响应自身声明的原始目标；“已登录”JSON 只作为同一 App 捕获窗口中的独立事实，不伪称已完成唯一连接关联。

## 4. 停用 MagicNet 对照

实际执行服务停止，并从机器接口确认：

- 生命周期为 stopped。
- sing-box 核心不运行。
- 透明代理数据面为 false。

随后重新启动校园 App，在该状态下仍捕获到上表两类业务目标的认证重定向，以及最终 HTML 响应。因此，当前会话下的认证阻断并不依赖 MagicNet 核心继续运行。

这一对照不证明所有历史网络故障与 MagicNet 都无关，也没有证明更换运营商、清除系统 DNS 缓存后的表现。它直接验证的是当前手机、当前网络和当前 App 会话。

## 5. 恢复步骤与验收

郑州大学信息化办公室的官方 FAQ 对“已登录后转圈、白屏”给出的处理是：进入“我的”，退出登录，然后使用账号密码重新登录；文档把长期登录导致认证密钥失效列为可能原因。[1]

下一步通过 App 正常登录流程重建会话。如果学校要求密码或短信验证，应由用户在手机上输入，不在报告或聊天中收集。

恢复后必须同时验证：

1. 首页或服务菜单实际出现内容。
2. 原先失败的日程等页面正常显示。
3. 对应业务调用不再被送到认证 HTML 页面。

在这三项通过前，不把“网络检查通过”“重启完成”或“登录页可打开”写成“校园 App 已修复”。

## 6. 配置与数据处理

本次没有发现足以支持修改 MagicNet TUN、全局 DNS、校园域名直连策略或证书校验的证据。临时关闭广告拦截的 UI 对照受前台切换影响，不能得出因果结论；原拦截选择已经恢复。

报告将在最终状态核验后补充服务恢复、临时探针卸载和调试文件清理结果。当前不发布新的 MagicNet 软件版本。
